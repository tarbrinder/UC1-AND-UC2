## 2. Testing methodology & yardsticks — how we guarantee nothing is missed

Coverage is defined as a **matrix product**, not a vibe. A test block must exist for every cell of:

```
DIMENSION  ×  SURFACE            ×  STATE           ×  CONDITION
─────────     ───────────────      ─────────────      ─────────────────────────
functional    Simple-popup         product            happy path
ui            Simple-standalone    specs              connection fails
ux            Category-popup       aispecs            LLM fails / times out / 401 key
failure       Category-standalone  more               API 4xx/5xx/empty/slow
race          Standard-mobile      OTP                buyer-spec API fails → seller-spec fallback
a11y          Standard-standalone  results            AI-specs fail → auto-skip
security       Standard-popup                         corpus loads late / never
compliance    (× mobile/desktop)                      mic↔photo↔typed permutations
tracking                                              back/forward/stepper-jump
perf                                                  refresh / browser-back / rotate
```

**Yardsticks (the "definition of done" per dimension):**
- **Functional** — every stage reachable & exitable; every transition (forward, back, stepper-jump, score-jump) lands correctly; no state desync; no data lost on navigation; submit produces correct requirement text.
- **Inputs** — *every* permutation of {type, mic, photo} × {first, after, clear-then-re-enter, concurrent, cancel, empty/garbled}. This is where your stale-mic bug lives.
- **Failure** — *every* external call × {4xx, 401 (key exhausted), 403, 429, 5xx, timeout, empty body, malformed body, slow/partial, offline, CORS}. Never stuck, never blank, never silent-success.
- **Race** — every effect guarded by `commitGen`/`aiEpoch`/`aiFiredFor`/`aiSkippedFor`; every await re-checked against a generation token; cross-dimension intersections (a jump *during* a load *during* a race).
- **A11y** — WCAG 2.1 AA: keyboard-only, focus trap, Escape, aria-live for dynamic text, labels, 4.5:1 contrast, 44×44 targets, 200% reflow, reduced-motion, SR announcement of errors.
- **Security** — no secrets in the bundle; prompt-injection containment; no PII in URLs.
- **Compliance** — consent/DND/privacy before identity submission; disclosure of third-party data sends.
- **Tracking** — every funnel event fires with correct props (§8).
- **Perf** — TTI, bundle, base64 payload memory, venue-network behavior.

**How we drove toward 100% (and proved it):**
- Round 1: 8 dimension investigators → 59 issues, 155 cases. Completeness critic rated it **74%**, named 13 gaps.
- Round 2: 6 gap-closers verified all 13 + fully audited StandardRFQForm + cross-dimension races → 50 issues, 79 cases, **25 refutations** (rigor: we prove non-bugs too). Verdict: **~92–95% in-scope**.
- Residual (minor) items are listed in §11 as explicit test cases, not hand-waved.

#### P0-01 · OWNER BUG CONFIRMED: mic/photo-extracted specs persist across name-clear/product-switch and autofill + feed BOTH LLM prompts for the NEW product
- **Where:** `src/components/SimpleRFQForm.tsx:224,399-402,454 (photoSpecsRef never wiped) + 294 (getSpecHints) + 313,322 (getMissingSpecs evidence) + 457-461 (direct autofill)`
- **What happens:** photoSpecsRef.current is JOURNEY-level and is never cleared on name-clear or product change (comment at 399-402 makes this intentional). When the buyer clears/changes the product name, applyExtractedSpecs already merged the mic/photo facts into photoSpecsRef (454), and commitProduct re-seeds pendingAiSpecs from it on the next commit (402). Those stale facts are then (a) autofilled onto the NEW product's page-1 ISQ fields via pendingAiSpecs + the [isqSpecs] flush effect (265-273) and the direct loop (457-461), (b) passed to getSpecHints as photoSpecsRef.current (294), and (c) passed to getMissingSpecs as evidenceSnapshot = {...photoSpecsRef.current} (313,322). So the mic's facts are STILL processed for a product the buyer switched away from.
- **Why it's a defect:** The 'lossless across a product change' design is only correct for spelling/name variants of the SAME category. When the buyer clears the name (explicit 'start over') or commits a DIFFERENT mcat, the old product's facts are wrong for the new schema and get submitted to sellers and used to generate the AI questions — incorrect data, exactly the owner's report.
- **Repro:** 1) Leave product blank, tap mic, say 'need 50 diesel generators, three phase, silent'. Mic commits 'Diesel Generator', quantity 50, specs {Phase:Three Phase, Enclosure:Silent} into photoSpecsRef. 2) Clear the product name field to empty. 3) Upload a photo of a water pump (or type 'Water Pump'). 4) On the specs/AI-specs pages the genset facts (Phase/Enclosure) are prefilled/asked about for the pump; getMissingSpecs receives them as evidenceFacts.
- **Fix direction:** Scope evidence to the product identity: tag each fact in photoSpecsRef with the mcatId it was extracted under and only reuse facts whose mcat matches the current mcatId; OR clear photoSpecsRef + pendingAiSpecs when the name is cleared in onProductInput (val.trim() empty) and when commitProduct resolves a different mcatId than the prior one.
- **Area:** MIC / PHOTO / TYPED-NAME INPUT RACES · round 1

- **Where:** `src/components/SimpleRFQForm.tsx:1197`
- **What happens:** The dashboard-popup surface renders `<div className="fixed inset-0 z-50 bg-black/40 backdrop-blur-sm overflow-y-auto" style={{WebkitOverflowScrolling:'touch'}}>` over MainApp's scrollable page (MainApp.tsx:99 = `min-h-screen ... py-16`). ## 10. Refuted candidates (checked against code — NOT bugs)

*Included as evidence of rigor: a paid auditor would raise these; we verified they're safe.*

- **Submit rapid double-tap opens OTP twice** — submit() (SimpleRFQForm.tsx:574) only does setShowOTP(true), and the modal is rendered by `{showOTP && <OTPGate/>}` (line 1216). showOTP is a boolean, so repeated setShowOTP(true) is idempotent and exactly one OTPGate ever mounts. Once open, the z-[200] full-screen overlay covers the Get Quotes button, blocking further taps. No path opens two OTP modals.
- **Re-entry from results via the all-clickable stepper re-submits the RFQ** — There is no submission to repeat. grep confirms SimpleRFQForm has NO localDB.saveSubmission, NO funnel/analytics, and NO network call on entering 'results' — it is a pure view. submit() with otpVerified.current===true just calls setStage('results') (idempotent). Re-entering results has zero duplicated side effects. (The related state-model defect — results sharing index 3 with 'more' — is reported separately at P3.)
- **A malformed ISQ row throws / white-screens the form** — The ISQ paths are defensively coded: mapDisplaySpecs (SimpleRFQForm.tsx:92-103) filters rows on truthy IM_SPEC_MASTER_DESC and Array.isArray-guards OPTIONS_DATA; deriveUnits (:368-373) filters to truthy IM_SPEC_MASTER_DESC; the GetIsq/getISQs fetches are wrapped in try/catch (:404-416) and .catch (:432). Every render-time isqSpecs.map(s => s.IM_SPEC_MASTER_DESC.toLowerCase()) (e.g. :783,:431) operates only on mapDisplaySpecs output, which guarantees the field is a non-empty string. A malformed row is dropped, not thrown on.
- **An unexpected LLM/n8n shape throws during render** — getMissingSpecs sanitizes every question (gemini.ts:1713-1731): fieldName is coerced to a trimmed string and empties are `continue`d, options defaults to []; getSpecHints wraps JSON.parse in try/catch (:1600). Both are consumed inside async .then/await with catch blocks (SimpleRFQForm.tsx:301,:329), never in render. So a bad shape yields empty/degraded UI, not a render throw. (Minor latent: JSON.parse('null') returns null and would bypass the string-catch at gemini.ts:1600/1681, but the call-site .catch handles it — noted in open questions, not a white-screen.)
- **A bad StandardProduct throws in StandardRFQForm render** — Within this app, product always comes from getStandardProduct(sid) (App.tsx:35) which returns either a well-formed entry from the hardcoded STANDARD_PRODUCTS map or null (and null is guarded before mounting the form). product.specs.map / new Set(product.specs.map(...)) (StandardRFQForm.tsx:60,:198) can only throw if a host passes a malformed product prop directly — not reachable via any in-app route. Latent only for external embedders.
- **Image upload has 'no MIME check' whatsoever** — Partially imprecise: the file input DOES carry accept="image/*" (SimpleRFQForm.tsx:1206), which is a soft picker filter. It is NOT a real guard (bypassable to 'All files' on desktop, and HEIC/large images pass it on mobile), so the underlying vulnerability is real — but the exact phrasing 'no MIME check' overstates it. The accurate statement is 'no ENFORCED MIME whitelist in code; only a bypassable accept hint.'
- **contactMobile is gated by 'length>=10 after digit-strip' in the Simple form** — Precise mechanism differs by surface: StandardRFQForm.tsx:134 is literally length>=10, but SimpleRFQForm caps the input at slice(0,10) and the real verification gate is OTPGate.tsx:59 using /^\d{10}$/ (exactly 10). The security substance (no 6-9 Indian-prefix rule; junk 10-digit numbers verify) is fully confirmed; only the '>=10' wording is inexact for the Simple surface.
- **submit() just flips to 'results'** — Imprecise mechanism, not a separate defect. submit() (SimpleRFQForm.tsx:574) only flips directly when otpVerified.current is already true (logged-in path); otherwise it opens OTPGate and the results flip happens in the onVerified callback at :1216. The NET claim (no real enquiry is ever dispatched) is confirmed and captured in the RI-01 finding, but the "just flips" wording understates the OTP detour.
- **LLM-output prompt injection is an XSS vector** — Refuted as XSS. grep confirms there is no dangerouslySetInnerHTML in SimpleRFQForm.tsx, StandardRFQForm.tsx, OTPGate.tsx, VoiceRecorder.tsx, or gemini.ts. All LLM-returned strings render as React text nodes / input placeholders, so injected `<script>`/`onerror` payloads render inert. The genuine risk is content/social-engineering steering of buyer-facing questions (see SEC-01), not script execution.
